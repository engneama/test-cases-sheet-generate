# Test Cases Sheet Generate – Claude Skill

Skill بتاخد **User Story / BRD / سكرين شوت / Figma / لينك** وتكتب منهم **Manual Test Cases** (Functional و Non-functional) بالإنجليزي في ملف Excel بنفس template الرفع بتاع الفريق بالظبط، ومعاه ملف **Coverage & Gaps** للمراجعة.

القاعدة الأساسية: بتكتب اللي البيزنس قاله وبس، وأي حاجة ناقصة بتسألك عنها بدل ما تخمّنها. الاستثناء الوحيد هو حالات **Security** و**Usability**، ودي بتتكتب دايماً حتى لو مش موجودة في الـ BRD.

## تشغّله إزاي
اكتب طلبك عادي وابعت معاه المدخلات. الـ skill بتشتغل لوحدها لما تلاقي جملة زي «اكتبلي test cases» أو «تيست كيسز» أو «شيت test cases» أو «write test cases». لو ماشتغلتش، اكتب اسمها `test-cases-sheet-generate` صريح في الطلب.

**مثال لطلب كامل**
```
اكتبلي test cases لفيتشر <اسم الفيتشر>
Project ID: <Project ID>
Parent Project Activity ID: <Parent Project Activity ID>
الـ BRD مرفق، وده لينك الصفحة على البيئة: <لينك dev أو UAT أو prod>
```
الـ skill مافيهاش أي لينك أو دومين أو فورم ثابت: البيئة والـ paths ودومين الإيميل والحسابات والحقول كلها بتتاخد من مدخلاتك، فتنفع مع أي سيستم وأي فورم.

## المدخلات
| المدخل | الصيغة | بياخد منه إيه |
|---|---|---|
| User Story / BRD / AC | نص ملصوق أو ملف docx / pdf / md / xlsx | السلوك المتوقع، القواعد، الرسايل، الحدود، الأدوار |
| سكرين شوت / Mockup / Figma | png / jpg / صفحة pdf / لينك Figma (أو frames متصدّرة لو مش هيقدر يفتحه) | الحقول والزراير واللينكات وعلامة * والرسايل الظاهرة وحالات العناصر (hover، disabled، error) |
| لينك الصفحة | أي بيئة: dev أو UAT أو prod | نفس عناصر السكرين شوت + الـ URLs الحقيقية |

- لو بعت أكتر من مدخل: الـ Story بتحدد السلوك والحدود، والسكرين شوت أو اللينك بيحدد أسماء العناصر. لو اختلفوا بيتحسب Gap وبيسألك.
- السكرين شوت لوحده بيوري الشاشة مش السلوك، فالنتيجة اللي مش مكتوبة بتطلع `Depend on BRD or User Story`.
- لو اللينك محتاج login أو VPN ومافتحش، هيطلب منك سكرين شوت بدل ما يخمّن.

## البيانات المطلوبة قبل البدء
ابعتها مع أول طلب. لو حاجة ناقصة هيسألك عنها في رسالة واحدة، ومش هيخمّن الـ IDs.

| البيان | بيروح فين |
|---|---|
| Project ID | عمود Project |
| Parent Project Activity ID | عمود Parent Project Activity |
| اسم الفيتشر | اسم الملفات |
| الأدوار (لو بتفرق) | تيست كيسز الصلاحيات |
| لينك البيئة: dev أو UAT أو prod (لو مابعتّش لينك) | أول خطوة في كل تيست كيس |
| دومين الإيميل وحسابات الاختبار (لو التيستات محتاجاها) | بيانات الاختبار جوه الخطوات |

لو عندك حدود مش مكتوبة في الـ BRD (أقل وأكبر طول، عدد أرقام، نوع وحجم ملف…)، اكتبها في الطلب. غير كده هتظهر كـ Gaps وهيسألك عنها.

## الـ Gaps وإزاي ترد عليها
الـ Gap حاجة التستر محتاج يختبرها والبيزنس ماحددهاش. الـ skill بتجمعها وتسألك قبل ما تكتب الملف، في شكل اختيارات تدوس عليها أو قايمة مترقّمة. تقدر ترد بالعربي عادي، مثلاً: `1 نعم، 2 لأ، 3 نعم والحد الأقصى 50 حرف`.

| نوع الـ Gap | مثال | بيتعامل معاه إزاي |
|---|---|---|
| سيناريو ناقص | إيميل متسجّل قبل كده، Back بعد الإرسال | بيسألك |
| قاعدة أو حد ناقص | مفيش أقل/أكبر طول أو فورمات | بيسألك ويطلب القيمة |
| Policy مش محددة | تعقيد الباسورد، CAPTCHA، OTP، حد للطلبات | بيسألك |
| دور أو صلاحية ناقصة | أكشن مش معروف مين مسموحله | بيسألك |
| تعارض | الـ Story والسكرين شوت مختلفين | بيسألك |
| كلام مش واضح | «الصفحة تكون سريعة»، «يتعمل validation على الحقل» | بيسألك عن تعريف أو رقم يتقاس |
| رسالة أو نتيجة ناقصة | نص رسالة النجاح أو الخطأ مش مكتوب | بيكتب التيست بـ `Depend on BRD or User Story` وبيبلّغك |
| قيمة Security / Usability | عدد المحاولات قبل القفل، مدة الـ timeout | بيكتب التيست دايماً وبيبلّغك |

- **نعم**: بيضيف التيست، وبيستخدم القيمة أو النتيجة لو إديتهاله.
- **لأ**: مش بيضيف تيست، وبيعلّمه `Not needed (user)` في شيت الـ Gaps.
- **مارديتش أو مش عارف**: مش بيضيف تيست، وبيعلّمه `Open – no answer` في شيت الـ Gaps وفي قايمة الـ business gaps اللي تترفع للبيزنس.

يعني الـ skill عمرها ما بتفترض: أي نقطة ناقصة أو مش واضحة يا إما بتسألك عنها، يا إما بتطلع gap.

## Security و Usability (دايماً، حتى لو مش في الـ BRD)
بيكتب كل حالة لما الشرط بتاعها يكون موجود في الفيتشر، وبيسيب اللي مالوش علاقة.

**Security** (Priority High)
- **Login**: قفل الحساب بعد محاولات غلط، إخفاء الباسورد، رسالة الخطأ ماتكشفش أنهي غلط الإيميل ولا الباسورد.
- **Session وصفحات محمية**: الـ session timeout، الـ Logout مع زرار Back، فتح URL محمي من غير login.
- **Roles**: فتح صفحة مش من صلاحية الدور بالـ URL.
- **حقول نصية**: XSS و SQL injection.
- **رفع ملفات**: ملف exe متنكر.
- **رابط ريست / OTP**: مايتستخدمش مرتين، والمنتهي يترفض.
- **Forgot password / تسجيل**: الرد مايكشفش هل الإيميل متسجل ولا لأ.
- **أي صفحة**: HTTPS، ومفيش باسورد أو توكن أو رقم هوية في الـ URL.

**Usability** (Priority Medium)
- **الفورم**: ترتيب الـ Tab، الـ focus، رسالة الخطأ جنب الحقل، البيانات ماتتمسحش بعد خطأ.
- **زرار الإرسال**: حالة تحميل، والدبل كليك مايبعتش مرتين.
- **اللينكات والزراير**: ظاهرة، والمؤشر بيتغير، وتتوصل بالكيبورد.
- **عربي وإنجليزي**: اتجاه RTL/LTR صح، ومفيش نص غير مترجم.
- **الجداول**: رسالة لما مفيش بيانات، والنص الطويل مايبوّظش الشكل.
- **أي صفحة**: شكلها على الموبايل، عنوان الصفحة، ورسالة بعد كل أكشن.

لو الحالة محتاجة قيمة أو نص مش محدد، بتتكتب بـ `Depend on BRD or User Story` وتظهر في قايمة الـ business gaps.

## لغة التيست كيس
التيست كيس بيتكتب **بالإنجليزي دايماً**، حتى لو الـ BRD والشاشة عربي بالكامل. بيفضل عربي بس اللي مكتوب عربي فعلاً على الشاشة، وبيتكتب بين علامتين تنصيص مرة واحدة من غير ترجمة بين أقواس.

| الجزء | اللغة |
|---|---|
| جمل الـ Title والـ Details والـ Expected Results | إنجليزي |
| أسماء عناصر الشاشة (حقول، زراير، لينكات، صفحات) | زي ما هي في المدخلات |
| نص رسايل النظام والإيميلات وعناوين الصفحات | زي ما بيظهر في الصفحة اللي بتتختبر |
| بيانات اختبار لحقل عربي (زي الاسم) | عربي |
| ملف Coverage & Gaps | إنجليزي |

**الشكل الصح** (اللي بين `< >` بيتملى من الشاشة اللي بتتختبر، بلغتها):
```
Title: Verify error message when entering an email without domain in the "<form>" form
- Open the "<page>" page <environment URL><path>
- Enter a not valid email without domain like ex: "<name>@" in the "<email field>" field.
- Click "<submit button>".
Expected Results: The error message "<exact message>" is shown under the "<email field>" field and the form is not submitted.
```
**أمثلة غلط**: `Click "النماذج (Forms)"` فيها ترجمة بين أقواس، و`- اضغط على زر إرسال` خطوة مكتوبة عربي.

## الملفات اللي بتطلع
**1. ملف الرفع `<Feature>_Test_Cases.xlsx`**: شيت واحد اسمه `Table 1`، أول صف فيه الـ 10 أعمدة دول بالترتيب، وكل صف بعده تيست كيس واحد. مفيش عمود ID ولا خلايا مدموجة ولا صفوف فاضية.

| # | العمود | القيمة |
|---|---|---|
| A | Activity Type | `Test Case` دايماً |
| B | Title | يبدأ بـ Verify + اللي بيتختبر + الشرط (5 لـ 12 كلمة تقريباً) |
| C | Details | الـ Preconditions وبعدها الخطوات، كل خطوة في سطر بيبدأ بـ `- ` والبيانات جواها |
| D | Expected Results | من الـ BRD أو ردّك، ولو مش محددة: `Depend on BRD or User Story` |
| E | Actual Results | `Depend on BRD or User Story` |
| F | Status | فاضي |
| G | Priority | High أو Medium أو Low |
| H | Project | الـ Project ID |
| I | Parent Project Activity | الـ Parent Project Activity ID |
| J | Format Text Editor Fields | `1` دايماً |

**2. ملف المراجعة `<Feature>_Coverage_and_Gaps.xlsx`** (مش للرفع):

| الشيت | بيوريك إيه |
|---|---|
| Requirement Coverage | كل requirement والتيست كيسز اللي بتغطيه وحالته (Covered / Partially Covered / Not Covered)، ومعاهم صفين SEC و USA |
| EP & BVA | كل حقل أو قاعدة، والـ partitions والـ boundary values اللي اتختبرت |
| Gaps | كل gap، والسؤال اللي يترفع للبيزنس، وقرارك فيه |

**3. ملخص في الشات**: المدخلات اللي استخدمها، وعدد التيست كيسز من كل نوع (EP، BVA، Security، Usability، Gaps)، وقايمة الـ business gaps اللي لازم تترفع للبيزنس.

## بيغطي إيه في كل Requirement
| نوع السيناريو | بيتكتب امتى |
|---|---|
| Positive | لكل requirement |
| Negative | للحقول والقواعد اللي المدخلات حددتها |
| Equivalence Partitioning | لكل قاعدة مذكورة |
| Boundary Value Analysis | لكل حد مذكور: الحد نفسه واللي قبله واللي بعده، كل قيمة في تيست لوحده. مثلاً لو الاسم من 3 لـ 50 حرف: 2، 3، 4، 49، 50، 51 |
| Role-based | لكل دور مذكور |
| Audit log | لو المدخلات ذكرته |
| UI | للعناصر الظاهرة في المدخلات، ومطابقتها للتصميم (الأسماء، الترتيب، الـ placeholders، الحالات) |
| Non-functional | لكل متطلب غير وظيفي ليه رقم يتقاس (أداء، متصفحات وأجهزة، accessibility). لو مفيش رقم بيسألك |
| Gaps | اللي قلت لها نعم بس |

الأرقام دايماً من الـ BRD، والـ skill مافيهاش أي حدود ثابتة.

## قواعد الجودة في كل تيست كيس
- **هدف واحد**: كل تيست بيختبر سلوك واحد بس.
- **مستقل**: مش بيعتمد على تيست تاني. فيه الحساب والـ Preconditions والـ URL وكل البيانات.
- **قابل للتنفيذ**: كل خطوة فيها بيانات بمثال `like ex:`، والنتيجة حاجة تتشاف (رسالة، صفحة، حالة حقل) مش «works correctly».
- **مفيش تكرار**: السلوك الواحد ليه تيست واحد، وبيتربط بكل الـ requirements اللي بتذكره.
- **الـ Negative لسبب واحد**: كل الحقول صح ما عدا الحقل اللي بيتختبر.
- **Priority**: High للفلوهات الأساسية والأمان والصلاحيات، Medium للـ validations والحدود والـ Usability، Low للحاجات الشكلية.

## نصايح وأسئلة متكررة
- ابعت الـ Story أو الـ BRD مع سكرين شوت أو لينك. الأول بيحدد السلوك، والتاني بيحدد أسماء العناصر بالظبط.
- راجع شيت الـ Gaps وارفع الـ business gaps للبيزنس، وبص على ملف الرفع قبل ما ترفعه، خصوصاً عمودي Project و Parent Project Activity.

**ليه فيه `Depend on BRD or User Story`؟** لأن المدخلات ماحددتش النتيجة، والـ skill مش بتخمّن. اسأل البيزنس وكمّلها.

**ليه فيه تيست كيسز Security و Usability مع إن الـ BRD ماذكرهاش؟** لأنها بتتكتب دايماً لما الشرط بتاعها يكون موجود في الفيتشر.

**ليه أسماء الزراير عربي والباقي إنجليزي؟** عشان التستر يلاقي الاسم على الشاشة زي ما هو بالظبط.

**عايز التيست كيسز في الشات مش في ملف؟** اطلب كده صريح، وهيرجعلك جدول بنفس الـ 10 أعمدة ومعاه جداول التغطية والـ gaps.

**عايز قيمة مختلفة في عمود معين (زي Status بعد التنفيذ)؟** قوله القيمة، وهيمشي على كلامك.
